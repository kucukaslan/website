Timing & scheduling assumptions

The proxy request and CPU request are two distinct incoming requests handled by the same client worker. The proxy calls the downstream server; the CPU request runs synchronous work. Both are in progress concurrently in the blocked cases, but at most one request coroutine executes on the thread at a time. The normal and slow-server controls omit the CPU request.

An await that must wait suspends its coroutine. The loop can then run another task or a callback. While the CPU request runs cpu_spin(1.0) without yielding, neither the proxy coroutine nor I/O and timer callbacks can execute. A readable socket and an overdue timer do not themselves interrupt it.

This is an explanatory simulation, not an instrumented dump of Python’s ready queue. The two request rows show coroutine state. The Ready queue contains work eligible for selection, and Executing now is the one shared thread. A request becomes Ready when its awaited operation completes (or cancellation wakes it), then Running when its resume callback is selected. At the wake-up step, the I/O or timeout callback still occupies the thread while it queues the request’s resume. A Ready request therefore does not imply a free thread. The queue is a schematic selection trace, not a recording of CPython’s internal FIFO queue or every transport callback. Socket readiness and an overdue deadline are shown outside the queue while CPU work prevents the loop from collecting them. The late-success scenario illustrates an outcome; its I/O and timeout micro-ordering is not established by the PoC logs.

Times are approximate and small gaps make the handoffs inspectable. Ready is an inert state before either request arrives. Admission, callback selection, and the first send are separate events at approximately 0 ms. Seeking to 0 or restarting returns to Ready. Some consecutive steps share the same rounded timestamp: handling a timeout and returning HTTP 504 occur around the same millisecond. Guided playback holds every step, including these, while compressing long waits. The elapsed-time slider remains linear and ends at the last event in each case.

In the body-reading case, the displayed late success is only one possible ordering. Receiving headers does not disable aiohttp.ClientTimeout(total=0.5). Body processing, buffering, timer cleanup and cancellation can produce a different outcome. The 500 ms timeout is below aiohttp’s default rounding threshold.

A return arrow from Running to Waiting shows that awaiting can repeat. Temporary wake-up paths connect completed operations to the affected request and its queued resume; they depict causation, not another execution thread. The timeout path stops at a barrier while CPU work occupies the loop. The labelled work token moves from the ready queue to the single execution slot when selected. Request identity colours stay consistent across the request rows and queue. The lower wall-clock trace is linear; the walkthrough holds important events and compresses waits. Moving network packets illustrate the direction of a transfer, not measured transit time or TCP segment boundaries. A packet reaching the OS buffer is distinct from Python reading it; no read animation crosses the occupied loop while CPU work runs.

The client and server are independent services, potentially different Kubernetes services or deployments in entirely different infrastructure. The client-side boundary includes its Python worker, its timeout, and its host operating system’s receive buffer; the buffer is outside Python, not part of the downstream server. The OS can receive TCP data while the client’s Python thread is occupied; buffer states here are illustrative, since the PoC logs sends rather than kernel occupancy. Connection pooling reuses transports and does not create independent execution threads.
