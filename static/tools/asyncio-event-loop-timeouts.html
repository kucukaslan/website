Timing & scheduling assumptions

The proxy request and CPU request are two distinct incoming requests handled by the same client worker. The proxy calls the downstream server; the CPU request runs synchronous work. Both are in progress concurrently in the blocked cases, but at most one request coroutine executes on the thread at a time. The normal and slow-server controls omit the CPU request.

An await that must wait suspends its coroutine. The loop can then run another task or a callback. While the CPU request runs cpu_spin(1.0) without yielding, neither the proxy coroutine nor I/O and timer callbacks can execute. A readable socket and an overdue timer do not themselves interrupt it.

This is an explanatory simulation, not an instrumented dump of Python’s ready queue. The callback row shows work that needs the loop; socket readiness and timer deadlines do not imply their Python callbacks have already been queued. Callback dispatch and request resumption are shown as separate stages. Their exact micro-ordering is implementation-sensitive.

Times are approximate and small gaps make the handoffs inspectable. Ready is an inert state before either request starts; the first send is a separate event at approximately 0 ms. Seeking to 0 or restarting returns to Ready. Some consecutive steps share the same rounded timestamp: handling a timeout and returning HTTP 504 occur around the same millisecond. Guided playback holds every step, including these, while compressing long waits. The elapsed-time slider remains linear and ends at the last event in each case.

In the body-reading case, the displayed late success is only one possible ordering. Receiving headers does not disable aiohttp.ClientTimeout(total=0.5). Body processing, buffering, timer cleanup and cancellation can produce a different outcome. The 500 ms timeout is below aiohttp’s default rounding threshold.

Moving packets illustrate the direction of a transfer, not measured transit time or TCP segment boundaries. A packet reaching the OS buffer is distinct from Python reading it; no read animation crosses the occupied loop while CPU work runs.

The client and server are independent services, potentially different Kubernetes services or deployments in entirely different infrastructure. The client-side boundary includes its Python worker, its timeout, and its host operating system’s receive buffer; the buffer is outside Python, not part of the downstream server. The OS can receive TCP data while the client’s Python thread is occupied; buffer states here are illustrative, since the PoC logs sends rather than kernel occupancy. Connection pooling reuses transports and does not create independent execution threads.
