Model assumptions & scheduling details

Both incoming requests share one event loop in one client Uvicorn worker. Downstream server runs in a separate process. CPU request spins synchronously for 1,000 ms inside an async def handler; this is not await asyncio.sleep(...), which yields control. “Available” means the loop can schedule callbacks, not that it is continuously using CPU.

aiohttp.ClientTimeout(total=0.5) covers the HTTP operation, including reading the body. Receiving headers does not disable it. A 500 ms timeout is below aiohttp’s default 5-second rounding threshold. The origin is simplified to request send / timeout start; sub-millisecond setup and network transit are omitted.

The before-headers case blocks immediately after outbound request headers are sent (drawn at 1 ms) and resumes at ≈1,000 ms. The body-reading case processes response headers at 5 ms, then blocks from 6 to 1,006 ms. These small offsets are illustrative. Guided playback holds each state change and compresses uneventful waits; the timeline and displayed elapsed time retain their actual linear scale. Bars share a linear time scale. Pale portions in the detailed timing lanes lie ahead of the cursor. The first-50-ms view uses a different, explicitly labelled linear scale.

The network lane models bytes becoming available in the OS receive buffer, separately from application consumption. The PoC logs response sending, not packet arrival or kernel buffer occupancy; the buffer interval is an explanatory model. In the slow-server case, the cancelled client need not receive or buffer the later response, although the server can finish its handler.

In the body-reading case, ready data and the overdue timer are resolved after the loop resumes. The displayed successful path does not prescribe their exact callback order: receiving data, protocol completion, timer cleanup, task resumption, and effective cancellation depend on implementation state. An overdue timeout can still fail a similar request. Neither blocked outcome is a cross-platform scheduling guarantee.

Connection pooling reuses transports; it does not give requests independent execution threads. More workers change which requests share a loop. Increasing a pool or changing HTTP clients does not remove synchronous work from that loop.
