A conventional PR diff shows what a branch changed. A post-merge diff shows what accepting the PR would change.
For integration-focused review, shouldn’t the latter be the primary view?


The trade-off, and how to reproduce it
Contribution diffs are useful for reviewing author intent and keeping comments tied to the source. Integration previews answer a different question, must be recomputed when either tip changes, and need conflict resolution before a final result exists. A preview is provisional; it is not evidence that the code is correct.
This illustration models a normal three-way merge with one merge base, text files and no custom merge drivers. Rebase, cherry-pick, merge options and repository configuration can change the outcome. It is a set of Git-verified examples, not a Git engine running in your browser.
git merge-tree --write-tree main feature
# Only if successful: use the returned tree ID below.
git diff main <tree-id>
The independent example contains four unchanged separator lines between settings. Without that separation, the original adjacent-line edits conflict in Git even though they affect different settings.


What Git hosts display · sources
GitHub documents three-dot PR diffs. Bitbucket Cloud also compares the merge base to the source. Bitbucket Server / Data Center switched from simulated-merge diffs in 6.x to merge-base diffs in 7.x. Host and version matter; this is not a claim about every review system.
